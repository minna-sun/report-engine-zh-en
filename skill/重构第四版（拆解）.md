# 📄 文件 1：系统设计-v6.4

## 系统设计-v6.4

**性质**：本文件描述自动化报告生成系统的**顶层架构设计**，包含模块划分、依赖关系、开发顺序、版本管理、交付部署等完整内容。
**维护规则**：当架构调整（新增/删除模块、改变开发流程）时更新本文件，独立维护。
**版本**：6.4 ｜ **最后更新**：2026-09-30

## 1. 设计目标

实现测试报告的一键自动生成，替代人工编制，确保格式统一、数据准确。系统支持多种物料类别（如某物料类别 DEMO-001 类、DEMO-002 类、DEMO-003 类），通过配置驱动实现快速扩展。

**v5.0 核心目标**：将 Word 文档操作从 win32com 迁移至 python-docx + OOXML，彻底解除对 Microsoft Office 的依赖，为跨平台/PLM 部署奠定基础。核心准备：
- **COM 隔离**：所有 Word 操作通过 `DocumentEngine` 抽象接口，业务层与文档服务层不直接依赖 COM；
- **数据源抽象**：`reference_service` 提供统一数据查询接口，未来可替换为其他数据源；
- **输出抽象**：`file_renamer`、`table_writer` 为本地文件系统实现，未来可替换为其他存储；
- **依赖精简**：核心业务可在无 Office 环境中运行。

## 2. 架构设计原则

- **模块化**：按职责拆分为独立模块，单模块代码尽量控制在 200 行以内。
- **高内聚低耦合**：每个模块只做一件事，模块间通过明确的数据结构交互。
- **可回滚**：每个模块独立备份，任一模块崩溃不影响其他模块。
- **交互与逻辑分离**：业务逻辑不依赖特定用户交互方式（命令行、GUI、API 均可调用）。
- **开放封闭原则**：新增测试类型时新增策略，不修改已有稳定模块。
- **策略驱动**：测试项目按类型分类，相同类型共用同一处理策略。
- **配置驱动**：系统按"三层配置架构"运行——物料类别级、目标文件夹级、全局级。新增类别或项目只需新增配置数据行，无需改代码。
- **零硬编码原则**：所有路径、设备编号、测试数据、配置参数均从配置文件或数据文件读取，禁止写死。
- **数据驱动**：测试项目列表通过遍历 `原始数据/` 文件夹自动发现。
- **分层职责总纲（v5.0）**：
  - 业务层（Processor / Strategy）描述"**报告要生成什么**"；
  - TemplateEngine 决定"**在模板哪里生成**"（配置驱动定位）；
  - DocumentEngine 决定"**如何操作文档**"（抽象接口）；
  - 具体 Engine（docx_engine）决定"**用什么技术实现**"。
  - **禁止**跨层调用：业务层不调 DocumentEngine，TemplateEngine 不调 OOXML。
- **物料类别必填约束**：物料信息表中的"物料类别"列为必填；为空或缺失时 `config_loader.py` 必须**跳过该记录**，禁止用默认值替代，被跳过记录须在日志警告。
- **走一步验收一步**：每个模块生成后须经用户验收，验收通过方可进入下一模块，严禁连续生成多模块后统一验收。
- **临时文件生命周期管理**：所有临时文件写入系统临时目录（项目专用子目录），禁止写入原始数据或工作目录；生成模块须提供带路径白名单的清理函数，仅删除本模块生成的临时文件，防止误删。

### 3.1 五层职责边界（强制约束）

| 层级 | 文件 | 允许做的事情 | 严禁做的事情 |
| --- | --- | --- | --- |
| ① 接口层 | `main.py` | 解析参数、路由、调用 report_engine | 操作文档对象、调用 DocumentEngine |
| ② 业务编排层 | `report_engine.py` | 调度 Processor/Strategy、收集结果 | 直接调用 DocumentEngine、处理 Word 细节 |
| ③ 业务处理层 | `processors/`、`strategies/` | 执行业务逻辑、产生业务指令 | 调用 DocumentEngine、操作段落/表格、导入 python-docx |
| ④ 文档服务层 | `template_engine.py` | 接收业务指令、配置驱动定位、调用 DocumentEngine | 暴露段落/表格对象给上层、包含业务逻辑 |
| ⑤ 文档技术实现层 | `docx_engine.py`、`ooxml_service.py` | 实现具体文档操作（python-docx/OOXML） | 包含业务逻辑 |

### 3.2 关键设计决策

**决策 1：GenericProcessor + strategy_registry**
原 4 类 Processor 代码约 90% 重复。统一使用 `GenericProcessor` 处理所有类型化测试章节的公共字段（Test Standards/设备表/Test Result/Result description 等），类型-specific 逻辑下沉到独立 `Strategy`；`strategy_registry.py` 维护策略名称到类的映射。新增测试类型只需新增 Strategy 文件 + 注册一行。

**决策 2：拆分 ChapterConfig / ChapterRuntime / ChapterContext**
原 `ChapterConfig` 同时承载静态策略配置（来自物料类别配置）与运行时数据（来自目标文件夹配置），二者生命周期不同。拆为：`ChapterConfig`（纯静态、可缓存）、`ChapterRuntime`（每颗料运行时数据）、`ChapterContext`（一次报告某章节的完整上下文 = 配置 + 运行时 + 物料类别 + 原始文件夹名）。

**决策 3：新增 TaskContext**
一次报告生成中 `record`、`folder_path`、`config`、`output_path` 需在多个 Processor 间传递。新增 `TaskContext` 作为纯数据容器（**不含 Word COM 对象**），保持纯数据，避免方法签名膨胀。

**决策 4：引入 DocumentEngine 接口层（v5.0）**
为 PLM 部署解耦 Word 操作，新增 `DocumentEngine` 抽象接口；`docx_engine.py` 为基于 python-docx + ooxml_service 的实现；`engine_factory.py` 固定返回 docx_engine 实例。业务层不感知底层技术实现，迁移可随时回滚（改配置一行）。

**决策 5：Processor/Strategy 通过业务指令而非直接调用 DocumentEngine（v5.0）**
Strategy 不直接调用 DocumentEngine 或 template_engine 的文档方法，而是返回结构化业务指令（如 `{"action":"insert_image", "section":..., "placeholder":..., "image_data":..., "width_cm":...}`），由 `template_engine` 解析后调用 DocumentEngine。Strategy 不导入 python-docx / lxml / DocumentEngine，业务层与技术实现完全解耦。

**决策 6：DocumentEngine 不含 find_bookmark()（v5.0）**
系统已采用配置驱动定位（物料类别配置表维护插入位置），不再依赖 Word 书签作为主定位机制；保留书签会诱导业务层依赖书签，与方向冲突。

**决策 7：放弃书签，改用占位符（v5.0）**
模板中写入 `{front}`、`{back}` 等纯文本占位符，脚本通过文本搜索在章节内定位（自动去括号），插入图片后保留占位符文本作说明标签。支持 `{}`/`[]`/`<>` 括号风格。配置表"书签列表"改名为"占位符列表"。

**决策 8：不实现页码自动更新（v5.0 定稿）**
页码由 Word 打开文档时自动计算（PAGE/NUMPAGES 域），更新页码依赖 COM，与解除 Office 依赖目标冲突。禁止在 DocumentEngine / template_engine / report_engine 中实现页码更新；必要时在导出 PDF 阶段处理。

### 3.3 业务指令流转机制（v5.0 核心机制）

**一、调用链数据流**
1. Strategy 生成业务指令（不操作文档），如：
   ```python
   # ImageBasedStrategy 内部
   def execute(self, template_engine, chapter_ctx, task_ctx) -> ChapterResult:
       image_data = self._find_image(chapter_ctx)          # 读取图片字节
       return {                                              # 业务指令（不执行文档操作）
           "action": "insert_image",
           "section": chapter_ctx.config.test_item,
           "placeholder": "front",
           "image_data": image_data,
           "width_cm": chapter_ctx.config.image_width or 7.0,
       }
   ```
2. template_engine 接收指令，配置驱动定位章节/锚点，调用 DocumentEngine。
3. DocumentEngine（docx_engine）执行具体操作（python-docx + OOXML）。

**二、业务指令数据结构契约（隐式契约）**

| Action 类型 | 关键字段 | 说明 |
| --- | --- | --- |
| `insert_image` | `section`, `placeholder`, `image_data`(bytes), `width_cm` | 在章节占位符处插入图片 |
| `insert_table` | `section`, `anchor`, `table_data`(dict), `width_cm` | 在锚点后插入表格（含 rows/styles/merged_ranges） |
| `copy_table` | `section`, `source_anchor`, `target_anchor` | 跨文档复制表格 |

**三、关键约束**
- 禁止 Strategy 返回 DocumentEngine 可执行对象（段落/表格）；
- 禁止 Strategy 导入 python-docx / lxml / OOXML；
- 允许 Strategy 导入 `models/` 与 `reference_service`（数据查询）；
- 禁止 template_engine 包含业务判断逻辑，仅做配置驱动定位。

### 3.4 Processor 与 Strategy 的调用

核心变化：
1. 五种以上测试类型统一使用 `GenericProcessor`，不再为每类写 Processor 文件；
2. `processor_registry.py` 只保留类型到 `GenericProcessor` 的映射；
3. `strategy_registry.py` 按 `ChapterConfig.strategy` 查找具体 Strategy；
4. `GenericProcessor` 只做公共编排（Test Standards/设备表/Test Result/Result description/Test Condition/Sample Number），再调度 Strategy；
5. Strategy 只做差异化业务（图片匹配、电性 Excel 转图、跨文档复制表格）；
6. Strategy 不直接操作 DocumentEngine，统一经 template_engine 完成文档操作。

调用链示例：
```
core/report_engine.py
    ↓ GenericProcessor.execute(doc, chapter_ctx, task_ctx)
    ↓ 按 chapter_ctx.config.strategy 查询 strategy_registry
ImageBasedStrategy.execute(template_engine, chapter_ctx, task_ctx)  → 返回业务指令
    ↓ template_engine 解析执行
DocumentEngine.insert_image(...)  →  docx_engine
```

Processor 与 Strategy 对应关系（类型 → Strategy 字段 → 文件）：

| 类型 | Strategy 字段 | 文件 |
| --- | --- | --- |
| ImageInspection | ImageBasedStrategy | image_based.py |
| ReliabilityCycle | ReliabilityCycleStrategy | reliability_cycle.py |
| Electrical | ElectricalTableStrategy | electrical_table.py |
| Compliance | ComplianceStrategy | compliance.py |
| ImageElectrical | ImageAndElectricalStrategy | image_and_electrical.py |
| ImageAuto | ImageAutoStrategy | image_auto.py |

## 4. 开发与调试顺序

### 4.1 核心纪律

- **走一步验收一步**：逐模块生成，每完成一个模块必须暂停等待用户验收，通过并备份后方可进入下一模块，严禁连续生成后统一验收。
- **200 行硬约束**：单模块代码不得超过 200 行（含空行注释）。超限须暂停说明（单一职责、为何超、预估行数），由用户决定允许超（不超 400）或拆分，严禁未经确认自行超出。
- **路径管理约束**：所有文件路径从 `config.yaml` 或 `config_loader` 读取，禁止写死绝对路径（如 `本地配置目录（如本地盘符路径）`）。
- **测试数据管理约束**：测试数据从 `test/` 目录读取，设备编号从目标文件夹配置或设备字典读取，禁止写死；验收后生产代码不留测试数据痕迹。
- **技术栈统一（v5.0）**：Excel 用 `openpyxl`（不支持 .xls，需先转 .xlsx）；Word 操作经 `DocumentEngine` 抽象层（python-docx + ooxml_service），禁止业务层直接导入 python-docx / lxml。
- **边界说明要求**：第 6 节每个模块须含"边界（不做什么）"字段，不得越界。
- **已验收模块只读**：验收备份后视为只读，不得主动修改；确需修改须先说明并获用户批准。

## 5. 数据来源说明

### 5.1 数据流向

物料信息表中的"物料类别"列为必填：
```
物料信息表
  ↓ config_loader 读取 → 筛选"审批状态=1"
  ↓ 检查"物料类别"列：有值→加入；为空/缺失→警告跳过（不生成报告）
main.py 只处理有物料类别的记录
  ↓ section_manager 按物料类别加载对应配置
  ├─ 找到配置 → 正常生成
  └─ 找不到 → 报错跳过（不使用默认值）
```

### 5.2 数据来源总览

| 数据 | 来源 | 获取方式 |
| --- | --- | --- |
| 编号列表 | 物料信息表 | 读取"审批状态=1"的编号 |
| 物料类别 | 物料信息表 | 读取"物料类别"列（如某物料类别 DEMO-001 类） |
| 策略配置 | `docs/数据库/物料类别配置/{物料类别}.md` | `section_manager` 按物料类别加载 |
| 测试设备/条件/样品编号/Result description | `{目标文件夹}/目标文件夹配置.xlsx` | `reference_service.load_folder_config()` |
| 设备完整信息 | `docs/数据库/设备字典.md` | `reference_service.get_equipment_detail()` |
| 翻译映射（部门/子类→英文） | `docs/数据库/翻译映射表.md` | `reference_service.get_translation()` |

## 6. 模块详细规格

**通用约束（所有模块适用）**：路径管理从 config 读取禁止硬编码；Excel 用 openpyxl，Word 经 DocumentEngine 抽象层；所有 .md 表格数据经 `reference_service` 统一接口读取，禁止各模块自行解析 Markdown。

### 6.0 数据模型层（models/）

仅定义数据结构，不含业务逻辑或 COM 对象；数据结构变更只改对应文件，引用自动生效。

- `models/material.py` → `MaterialRecord`：物料信息表一条记录（number、material_category、material_code、material_subclass、material_model、creator、department、description、quantity、receive_date、sample_count、supplier、approval_status 等）。
- `models/chapter.py` → `ChapterConfig`（静态策略配置：test_item、category、strategy、folder_name、placeholders、image_mapping、standard、image_width）；`ChapterRuntime`（运行时数据：device、condition、result_description、sample_number）；`ChapterContext`（config+runtime+material_category+source_folder_name）。
- `models/result.py` → `ScanResult`/`ReportResult`/`GenerationSummary`/`ChapterResult`（含 test_item、test_basis、sample_number、test_result、result_description、status、error）。
- `models/context.py` → `TaskContext`（纯数据：record、folder_path、config、output_path）。
- **边界**：不含业务逻辑、文件操作、COM/连接等运行时资源。

### 6.1 基础设施层

#### `common/exception.py`
定义自定义异常树，根异常 `ReportPlatformError`，下含 `ConfigError`/`MaterialTableError`/`FolderNotFoundError`/`ExcelError`/`WordOperationError`/`TemplateError`/`ReferenceError`。
**边界**：不含业务逻辑，不处理异常输出，所有异常接受可选 `cause` 保留链路。

#### `common/logger.py`
统一日志格式与级别控制，提供 `info()/warning()/error()/debug()`；支持 `set_number(number)` 注入编号前缀、`apply_config(config)` 解析 `log_level`/`log_root`、双 Handler（控制台 INFO+，文件 WARNING+）。
**边界**：不负责业务逻辑与异常输出内容（由调用方传文本）。

### 6.2 数据获取层

#### `config_loader.py`
**用途**：加载 config.yaml、读取物料信息表、筛选已审批记录、**强制校验物料类别**（作为加载策略表的路由键）。
**关键接口**：`load_config(tool_dir?) -> (dict, list[MaterialRecord])`，返回配置字典与"已审批且物料类别非空"的记录列表。
**核心逻辑（泛化）**：定位配置文件与物料表 → 模糊匹配列名 → 从"变更描述"提取料号/物料子类/物料型号（优先精确提取料号后中文，失败兜关键词列表）→ 筛选审批状态=1 → **物料类别为空则跳过，无默认值** → 物料类别规范化去 `.0` 后缀。
**边界**：不处理业务逻辑，不为缺失物料类别提供默认值，不判断配置是否存在。

#### `folder_scanner.py`
**用途**：在数据目录下查找编号对应目标文件夹（纯物理路径发现，不执行业务筛选）。
**关键接口**：`scan_folders(approved_records, target_base, recursive=True, max_depth=4) -> list[ScanResult]`。
**边界**：不查文件夹内文件，不判数据完整。

#### `excel_table_builder.py`
**用途**：从 Excel 读取数据（含样式）构建结构化 Word 表格数据（纯 Python，不依赖 win32com）。
**关键接口**：`build_table_data(folder_path?, xlsx_path?, table_width_cm=18.0, skip_columns=(), skip_rows=(), require_header=True, force_font_name=None, force_font_size=None) -> dict | None`，返回 `{"rows":..., "styles":..., "merged_ranges":..., "width_cm":..., "images":...}`。
**边界**：不插入 Word、不渲染列宽、不判数据有效性；仅提取与格式转换。典型调用（泛化）：
```python
table_data = excel_table_builder.build_table_data(
    folder_path, "某电性子文件夹",
    table_width_cm=18.0, skip_columns=(), skip_rows=(),
    require_header=False, force_font_name="Times New Roman", force_font_size=10.5,
)
```

### 6.3 业务编排层

#### `core/report_engine.py`
**用途**：报告生成引擎，**纯调度器**。经 `DocumentEngine` 获取文档句柄，按固定顺序串联 Processor，不直接操作 Word。
**关键接口**：`generate_report(template_path, record, folder_path, output_path, config, report_language) -> ReportResult`（status/report_path/final_verdict/error）。
**执行流程（泛化）**：复制模板 → `engine.open()` → 建 TaskContext（doc 局部持有，不进 TaskContext）→ sample_processor → section_manager.build_chapters → template_engine.sync_chapters → 遍历章节调 GenericProcessor（公共填充+Strategy 调度，单章失败记错继续）→ summary_processor → highlight_expired_calibrations → `engine.save()` → `engine.close(doc)`（finally 中）→ 返回 ReportResult。
**一票否决项**：`engine.close(doc)` 必须在 finally；任意 return 前释放资源；单章节失败继续；最终结论只依赖 test_result。
**边界**：不负责章节内容填充、电性提取、图片处理、重命名、配置加载、文件夹扫描、章节决策、Word 细节；只负责调度、异常、返回统一结果。

#### `core/task_manager.py`（可选）
**用途**：任务生命周期管理，创建 TaskContext、汇总结果、统一异常包装（仅当 report_engine 超 200 行时使用）。
**关键接口**：`create_task_context()` / `summarize_results(chapter_results)` / `wrap_exception(error)`。
**边界**：不持有 Word 对象、不含业务逻辑、不操作文档。

### 6.4 入口与输出层

#### `main.py`
**用途**：主入口，串联所有模块，一键运行；对外暴露可编程函数与命令行入口。
**关键接口**：
- `run_report_generation(excel_path, base_path) -> GenerationSummary`（编程调用，无交互、无 input，返回结构化数据）；
- `main()` 命令行入口（批量模式 / 拖拽模式，拖拽模式绕过审批强制处理单个文件夹）。
**核心逻辑（泛化）**：判断调用方式 → 批量模式读 config.yaml 筛选已审批、递归扫描目标文件夹；拖拽模式从文件夹名提取编号强制处理 → 遍历每个 ScanResult：output/ 预检查防重复 → 自动发现唯一 .docx 模板 → 决策报告语言（三级优先级：物料表指定→模板识别→默认 en）→ 调用 `core/report_engine.generate_report()` → 重命名（`file_renamer`）→ 回写输出时间（`table_writer`）→ 创建快捷方式（纯 Python 库）→ 汇总 GenerationSummary。
**边界**：可编程接口不含交互代码；不负责重命名字段提取、模板文件名硬编码、Word 细节、语言识别算法具体实现。

#### `file_renamer.py`
**用途**：报告重命名。从 record 提取收样年月/料号/供应商/子类/型号/流程编号，拼接 `{收样年月} {料号} {供应商} {物料子类} {物料型号} {流程编号(R前缀)} {PASS/FAIL}.docx`，`os.rename()`。
**边界**：不生成结论、不移动文件。

#### `table_writer.py`
**用途**：报告成功后回写输出时间到物料信息表「报告输出时间」列（openpyxl，不依赖 COM）。
**关键接口**：`write_output_time(table_path, number, output_time=None)`。
**边界**：不判断调用时机、不创建表/列（仅追加列）、不验证流程号；失败仅警告不影响主流程。

### 6.5 文档引擎层（services/）

#### `services/document_engine.py`（抽象接口）
**用途**：定义文档操作标准化抽象接口，屏蔽底层技术差异。仅 `template_engine` 与 `report_engine` 经 `engine_factory.get_engine()` 获取实例。
**实现约束**：具体实现须遵循全部契约；禁止引入业务语义（如"哪些章节分页"由上层决定）。
**接口契约（按功能分组，方法返回 False/None 表示失败不抛异常）**：
- 生命周期：`open(source)` / `save(doc, path)` / `close(doc)` / `export_pdf(docx_path, pdf_path)`（附加工具，依赖本地 Office，仅 Windows，不阻塞部署）；
- 导航定位：`find_section`(加粗+文本匹配,有缓存) / `find_paragraph`(子串) / `find_placeholder`(精确) / `find_table` / `list_sections` / `find_paragraph_by_text` / `find_section_range` / `has_page_break_before` / `invalidate_section_cache`；
- 图片：`insert_image(doc, anchor, image_data, width_cm)`；
- 表格：`insert_table` / `copy_table` / `set_table_format`(禁用自动调整) / `set_table_autofit` / `set_table_cell_margins` / `add_table_row` / `remove_table_row` / `table_row_count` / `set_cell_text` / `set_cell_text_preserve` / `table_cell_text` / `table_column_count` / `set_text_color`；
- 文本结构：`insert_text`(冒号后替换) / `replace_paragraph_text` / `set_paragraph_color` / `set_paragraph_runs` / `replace_in_paragraph` / `add_page_break` / `delete_section` / `delete_section_content` / `clone_section` / `insert_text_in_header` / `set_adjacent_cell_text`；
- 遍历与过期标红：`iter_paragraphs` / `iter_tables` / `color_expired_in_paragraph` / `color_expired_in_table` / `color_expired_in_cell`。
**与 v4.x 差异**：已删除 `find_bookmark()`/`update_page_numbers()`；新增 `find_placeholder()`/`set_cell_text_preserve()`/`set_paragraph_runs()` 等。

#### `services/docx_engine.py`（主入口·实现）
**用途**：DocumentEngine 的 python-docx + ooxml_service 实现，唯一真正操作 Word 底层 XML 的技术实现者；不依赖 win32com/Office，跨平台，无 COM 残留。
**边界**：不含业务逻辑、数据查询；所有 find_* 不依赖书签；方法失败返回 False/None。
**子模块拆分（Mixin 组合）**：原文件按职责拆为 5 个子模块，外部导入路径不变（`from services.docx_engine import DocxEngine`）：
```python
class DocxEngine(NavigationMixin, ImageOpsMixin, TableOpsMixin, StructureOpsMixin):
    def __init__(self): self._section_cache = {}
    def open(self, source): ...          # 生命周期（本类实现）
    def save(self, doc, path): ...
    def close(self, doc): ...
    def export_pdf(self, docx_path, pdf_path): ...  # 仅 Windows+Office
```
- `docx_navigation.py`：章节/段落/表格/占位符定位与缓存；
- `docx_image_ops.py`：锚点处插入图片（居中、锁纵横比，表格内自动改行高 atLeast）；
- `docx_table_ops.py`：表格创建/复制/列宽/行列/单元格样式，按视觉宽度分配列宽、补边框；
- `docx_structure_ops.py`：文本插入/替换/着色、章节增删、分页符、日期过期标红；
- `docx_helpers.py`：纯工具函数（单位换算、段落判定、日期正则、深拷贝表格等），无状态。

章节同步黑名单保护（非测试章节前缀匹配，不被删除/新增）：Test Report/Statement/Sample Description/Sample Picture/Summary of Results/Remarks/Conclusion/The End 及对应中文标题。

#### `services/ooxml_service.py`
**用途**：docx_engine 的底层技术支撑，处理 python-docx 不直接支持的高级 OOXML 操作（跨文档复制表格、删除节点、精确列宽、合并单元格等），只对 docx_engine 开放。
**关键函数（签名级）**：`copy_table_to_doc(...)` / `delete_table(...)` / `set_table_column_width(...)` / `get_merged_cells(...)` / `set_cell_background(...)` / `set_text_color(...)` / `insert_page_break(...)` / `delete_paragraph(...)` / `add_image_to_rels(...)`。
**原则**：纯函数/无状态，输入为 lxml 节点或路径，失败返回 False/None，不含业务逻辑。

#### `services/engine_factory.py`
**用途**：工厂，固定返回 `DocxEngine` 实例（v5.0 定稿不再多引擎切换）。
**关键接口**：`get_engine() -> DocumentEngine`。
**边界**：不负责引擎初始化参数、生命周期管理、异常处理。

#### `services/language_detector.py`（可选）
**用途**：从模板封面关键词识别报告语言（zh/en）。`detect_language(template_path) -> "zh"|"en"|None`。
**边界**：仅初判，最终决策权在 main.py 三级优先级。

#### `services/language_pack.py`
**用途**：集中维护中英文模板锚点标签，禁止业务代码散写语言标签。
**关键接口**：`normalize(lang)` / `labels(lang)` / `pick(lang, key)` / `summary_col_keys()`。分组含 header/cover/sample/equip/chapter/summary/col/verdict/halogen 等。
**边界**：纯数据，不依赖 python-docx/openpyxl/win32com，无业务逻辑。

### 6.6 文档服务层（services/）

#### `services/template_engine.py`
**用途**：文档服务适配层，为业务层提供文档操作标准化工具函数。接收业务调用 → 按三层配置架构确定"在模板哪里操作" → 调用 DocumentEngine。
**核心原则**：业务层说"生成什么"，TemplateEngine 说"在哪里生成"（配置驱动定位），DocumentEngine 说"如何操作"，docx_engine 说"用什么技术"。
**边界（强制）**：不暴露文档对象给上层；不包含业务逻辑/策略选择/流程编排；不导入 python-docx / lxml / win32com；方法签名不出现 DocumentEngine 类型。
**模块级活跃文档状态**：维护 `_DOC`/`_ENGINE`，调用方处理文档前须 `set_active_doc(doc)`；占位符 helper（`insert_image_at_placeholder` 等）依赖此状态（非线程安全，单文档串行）。
**公开方法（按组）**：
- 章节同步与分页：`sync_chapters(doc, chapter_contexts, default_chapter_template, lang)` / `add_page_break(doc, test_item)` / `find_section_range(doc, section_name)`；
- 文本/图片/表格填充：`insert_text_after(doc, section, label, value, ...)` / `insert_image(doc, name, img, width_cm)` / `insert_image_after_text(...)` / `insert_excel_table_after_text(...)` / `insert_table_cell_value(...)` / `copy_table_from_doc(...)` / `copy_table_by_source_para_from_doc(...)` / `fill_equipment_table(doc, section, equipment_info, lang)`；
- 占位符 helper（无 doc 参数）：`insert_image_at_placeholder(placeholder, img, width_cm, section_name=None)` / `insert_text_at_placeholder(placeholder, text)`；
- 汇总与过期标红：`fill_summary(doc, chapter_results, lang)` / `fill_sample_description(doc, task_ctx)` / `highlight_expired_calibrations(doc)`；
- 全自动图片表格：`insert_image_auto_table(doc, section, image_list, width_cm, anchor_para=None)` / `insert_excel_images_after_table(...)` 等；
- 模块级状态：`set_active_doc(doc)`。
**通用行为**：文本填充为"冒号后替换"模式；插入在锚点段正下方；定位失败记警告不中断。

### 6.7 业务处理层（processors/ & strategies/）

> v5.0 约束：Processor/Strategy 不直接依赖 DocumentEngine，只调用 template_engine 或产生业务指令。除 ReliabilityCycle 外插入图片策略均按"显示宽度×200 DPI"压缩。

#### `processors/generic_processor.py`
**用途**：处理所有类型化测试章节，负责统一章节分页与跨类型公共字段填充，再按 `chapter_ctx.config.strategy` 调度具体 Strategy。
**关键接口**：`execute(doc, chapter_ctx, task_ctx) -> ChapterResult`。
**核心逻辑（泛化）**：① 章节分页；② Test Standards 填充（取自 config.standard，Compliance 跳过）；③ 设备表填充（来自 runtime.device，空则跳过，多设备拆分，查 reference_service，Compliance 跳过）；④ Test Condition 填充；⑤ Sample Number 填充；⑥ Result description 填充（Compliance 跳过）；⑦ Test Result 判定（reference_service.determine_test_result，FAIL 标红，Compliance 执行判定但跳过文档填充）；⑧ 冒号全/半角自适应；⑨ Strategy 调度（查 strategy_registry，未找到警告跳过）；⑩ 返回 ChapterResult。
**边界**：不负责章节分页以外文档细节、设备数据/翻译查询（由 reference_service）。

#### `strategies/base.py`
**用途**：所有策略统一抽象基类。
```python
class BaseStrategy(ABC):
    @abstractmethod
    def execute(self, template_engine, chapter_ctx, task_ctx) -> ChapterResult: ...
```
**约束**：Strategy 不导入 python-docx / lxml / DocumentEngine，只产生业务指令由 template_engine 执行。

#### `strategies/image_based.py`
**用途**：图片型策略，按配置驱动在章节内查找占位符，将匹配图片插入占位符位置。
**核心逻辑（泛化）**：读 config（test_item/source_folder/placeholders/image_mapping/width_cm）→ 定位原始数据子目录（仅当前层、不递归、排除系统文件）→ 扫描图片 → 解析映射 → 三轮匹配（精确/子串/模糊近义）→ 调用 `template_engine.insert_image_at_placeholder()` 插入，失败保留模板原样并记警告。
**边界**：不负责分页/公共字段/图片裁剪/Word 底层插入/章节存在判定。

#### `strategies/image_auto.py`（全自动图片）
**用途**：自动扫描图片文件夹，不依赖占位符与名称映射，在 Result description 后建表插图（固定 2 列，宽>9cm 占整行、≤9cm 两两配对；图片占 2 行：名称灰底+图片）。
**边界**：不导入 python-docx/lxml/DocumentEngine，与 ImageBasedStrategy 并存不替代。

#### `strategies/electrical_image_auto.py`（电性+全自动图片）
**用途**：同一章节先插电性表格、再插全自动图片表格，中间夹空行；两部分独立容错。

#### `strategies/ion_contamination.py`（离子污染）
**用途**：针对某物料类别（如 1025 类 / PCB 类器件），从离子污染源报告（PDF）匹配报告，拷贝到原始数据目录并提取方框图插入对应章节。
**核心逻辑（泛化）**：从文件夹名解析料号/周期号/供应商 → 四级优先级匹配候选 PDF（文件名须含料号+周期号，再按 AP/供应商要素升级）→ 命中后拷贝 PDF、提取图片（裁剪坐标图或整页）、插入 Word、清理临时图片。纯扫描件不读 PDF 内容，判定只看文件名。
**边界**：不导入 python-docx/lxml/DocumentEngine，不执行设备匹配。

#### `strategies/reliability_cycle.py`
**用途**：可靠性策略，从电性 Excel 读取（含行列过滤、样式保留）导出 PNG，裁剪白边后插入 Result description 下方；策略自完成流程，template_engine 仅提供 `insert_image_after_text()`。
**边界**：不负责分页/公共字段/设备查询；不调用 image_service（走 data_extractor，不经压缩）。

#### `strategies/electrical_table.py`
**用途**：电性策略，从 Excel 读全量数据（不跳行列）构建 Word 表格插入 Result description 下方；与 ReliabilityCycle 区别：不跳 B/C 列、不跳 22~27 行、输出 Word 表格而非 PNG。
**边界**：不负责分页/公共字段/设备与标准查询/表格样式细节。

#### `strategies/compliance.py`
**用途**：合规策略，从 RoHS 源报告复制数据表与设备表（本地优先→远程 fallback），不执行设备匹配。
**核心逻辑（泛化）**：读 config → 查找 RoHS 源报告（本地优先：文件夹名含 rohs，优先文件名含料号；远程：按 月→日 遍历 halogen_source_base 类根路径）→ 拷贝到本地 → 跨文档复制数据表与设备表（ooxml_service 深拷贝 w:tbl，不依赖剪贴板/COM）。数据表失败→skipped，设备表失败仅警告。
**边界**：不负责分页/公共字段/测试标准查询/表格格式调整。

#### `strategies/halogen.py`（卤素）
**用途**：从卤素源报告复制"Sample Test Result:"下第一个表格插入目标章节；与 Compliance 差异：源文档全局搜加粗段落锚点、直接插入（无旧表）、仅 1 表、中文报告全表翻译（引号归一化，数字/单位/＜RL 不译）。
**边界**：不导入 python-docx/lxml/DocumentEngine，不执行设备匹配，不处理 Test Standards/Result/Number。

#### `strategies/image_and_electrical.py`
**用途**：图片+电性复合策略，先插图片（委托 ImageBasedStrategy）再插电性表格（委托 ElectricalTableStrategy），两部分独立容错。
```python
class ImageAndElectricalStrategy(BaseStrategy):
    def __init__(self):
        self._image_strategy = ImageBasedStrategy()
        self._electrical_strategy = ElectricalTableStrategy()
    def execute(self, template_engine, chapter_ctx, task_ctx):
        try: self._image_strategy.execute(...)       # 失败仅警告
        except Exception as e: warning(...)
        try: self._electrical_strategy.execute(...)  # 失败仅警告
        except Exception as e: warning(...)
```
**边界**：不负责分页/公共字段/设备与标准查询。

#### `strategies/eds.py`（EDS）
**用途**：遍历原始数据子文件夹下各子文件夹，每文件夹按"图片表格→Excel 表格"插入，总汇总置顶，子文件夹独立成页（取点图优先）。
**边界**：不导入 python-docx/lxml/DocumentEngine，无图子文件夹跳过图片表格，单文件夹失败不影响其他。

#### `processors/sample_processor.py`
**用途**：步骤1~3（页眉、封面、Sample Description）的业务编排与数据准备，由 report_engine 直接调用（非类型化处理器）。
**核心逻辑（泛化）**：① 页眉填 Report No.（编号+送样次数字母）；② 封面填 Applicant（英文工号）/Applicant Department（中英文翻译）/Received Date/Inspection Date/Report Date（MM/DD/YYYY）；③ Sample Description 委托 `template_engine.fill_sample_description()`（按语言切换锚点，图片按 1-1/1-2 匹配）。保留数据转换函数（_sample_count_letter/_format_date/_strip_creator 等）。
**边界**：不负责文档定位写入（template_engine）、翻译维护、图片处理、Word 底层、数据正确性判断。

#### `processors/summary_processor.py`
**用途**：步骤5 汇总页生成，仅做数据统计（过滤、统计 PASS/FAIL/Reference、判定最终结论），统计后调 `template_engine.fill_summary()` 完成填充。
**核心逻辑（泛化）**：过滤 Sample Description → 统计总数/PASS/FAIL/Reference 填入统计段落 → 填 Test Contents 表格 → 判定最终结论（存在 FAIL→FAIL 否则 PASS，章节失败不影响）→ 填 Notes on FAIL/Reference（来自各章 result_description）→ 自动管理表格行 → 返回 final_verdict 供重命名。
**边界**：不判 Test Result 正确性、不生成 Test Basis、不负责重命名。

### 6.11 数据查询与图片服务

#### `services/reference_service.py`
**用途**：统一数据查询接口，屏蔽来源细节；所有 .md 表格数据必须经此读取，禁止各模块自行解析 Markdown。
**依赖**：设备字典.md / 翻译映射表.md / 物料类别配置/{material_category}.md / 目标文件夹配置.xlsx / openpyxl / re / os。
**关键接口（签名级）**：
- `load_folder_config(folder_path) -> dict`：读目标文件夹配置.xlsx，以"测试项目"列为键返回完整字典；
- `get_equipment_detail(asset_id, lang="en") -> dict`：设备字典精确匹配，失败填 "/"；
- `get_standard(material_category, test_item) -> str`：物料类别配置查测试标准，失败回退索引.md；
- `get_translation(field_type, value, lang="en") -> str`：翻译映射表查部门/子类英文，zh 直接返回原文，失败返回 `[缺失:...][TR]`；
- `get_subclass_translation(material_subclass) -> str`：子类→英文；
- `determine_test_result(folder_name) -> str`：按文件夹名后缀判定 PASS/FAIL/Reference（默认 PASS）；
- `find_actual_folder(folder_path, norm_name) -> str|None`：关键词包含匹配子文件夹；
- `get_pcb_supplier_id(name) -> str`：PCB 供应商映射归一化标准 ID。
**特殊规则**：内存缓存（同文件夹/同 md 仅解析一次，进程内有效）；Excel 自动扫前 6 行找"测试项目"表头；回退机制；占位符格式统一 `[缺失:...][TR]`。
**边界**：不验证数据有效性、不判设备是否存在、不修改写入、不为缺失运行时数据提供默认值、不维护映射表。

#### `services/image_service.py`
**用途**：统一图片处理——裁剪白边 + 按显示宽度重采样（可选）+ 按原格式保存。
**关键接口**：`process_image(img_path, target_width_cm=None) -> processed_img_path`（位于系统临时目录），`cleanup_processed(img_path)`（仅删临时目录内文件）。
**核心逻辑（泛化）**：PIL 读取 → 保存原 DPI → `_trim_white_borders`（裁白边，面积<5% 回退）→ 若传 target_width_cm 则按"显示宽度×200DPI"等比缩小（只缩不放）→ 按原格式保存（JPG→JPEG 质量90；其他→PNG）→ 输出临时目录。
**边界**：不判图片是否该处理、不插 Word、不调 DPI 元数据、不负责临时文件清理决策（由调用方传参决定）；ReliabilityCycle 不走本模块。

#### `data_extractor.py`
**用途**：从电性 Excel 读取（含行列过滤、样式保留）用 openpyxl+PIL 生成 PNG（纯 Python，不依赖 win32com）。输出 `{"image_path", "col_count"}` 或 None。
**边界**：不插 Word、不判图片宽度、不负责临时文件清理。

#### `services/pdf_extractor.py`
**用途**：从 PDF 提取文本/图片供 IonContaminationStrategy（依赖 PyMuPDF/fitz）。源报告为纯扫描件，`get_text()` 返回空，采用整页截图+按比例裁切。
**关键接口**：`extract_text(pdf_path)` / `extract_main_image(pdf_path, output_path=None)`（按页面高度比例裁切坐标图区域）/ `extract_full_page(pdf_path, output_path=None)`（截整页）。
**边界**：不解析 PDF 内容、不负责临时文件清理（由调用方在插入 Word 后删除）。

### 6.12 章节管理

#### `section_manager.py`
**用途**：扫描 `原始数据/` 文件夹，匹配物料类别配置，确定"有哪些章节"；加载目标文件夹配置，组装 `ChapterContext`。
**关键接口**：`build_chapters(folder_path, record) -> list[ChapterContext]`。
**核心逻辑（泛化）**：读 record.物料类别 → 加载 `docs/数据库/物料类别配置/{物料类别}.md` → 解析测试项目/文件夹名/类型/strategy/占位符/图片匹配/测试标准/图片宽度 → 扫描原始数据子文件夹 → 规范化匹配（精确+`_strip_suffix`+逐段剥尾部兜底）→ 按数字前缀自然排序（RoHS 强制置尾）→ 调 `reference_service.load_folder_config` 组装 ChapterRuntime → 创建 ChapterContext。

## 四、验收要点速查

### 4.1 通用验收项

- □ 代码符合 PEP8，有完整 docstring

- □ 禁止跨层调用（业务层不调 DocumentEngine）

### 4.2 report_engine.py 一票否决项

| 验收项 | 通过标准 |
| --- | --- |
| engine.close(doc) 在 finally 块 | 任何代码路径都能退出 |
| 任意 return 前确保资源释放 | 不允许 COM/进程残留 |
| 单章节失败→继续处理其他 | 不放弃整份报告 |
| 章节失败不影响最终结论 | 只依赖 test_result 字段 |
